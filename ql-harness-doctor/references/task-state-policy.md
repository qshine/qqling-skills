# 任务状态与异常恢复检查

用户于 2026-09-13 确认。适用于多工作项、跨会话或可能中断的需求实现，沿用 HD-STA-001、HD-STA-003、HD-STA-005，不增加控制或重复计分。每次手动诊断分别说明下表子检查的状态、理由与证据；整项控制必须覆盖其适用子检查后才能判为已满足。

## 必查流程

| 子检查 | 归属 | 要求与可观察证据 |
| --- | --- | --- |
| plan-before-implementation | HD-STA-003 | 实现需求前先建立或更新持久化权威清单。记录任务 ID、目标行为、验收方式、状态和依赖；已有清单则复用，不能只保存在聊天或内存中。 |
| persist-start-before-edit | HD-STA-003 | 开始某工作项的实际实现前，先将其状态持久写为 in_progress。通过任务关联记录核对更新先后；默认一个进行中项，隔离/所有权例外按 HD-SCP-001 判断。 |
| persist-done-after-check | HD-STA-003 | 每项实现并验证后，先持久写入 done、实际验证时间/结果与下一步，再开始下一项；不能等会话结束批量回写。 |
| gate-done-and-reopen | HD-STA-005 | done 必须绑定适用验证证据。验证失败保持 in_progress，外部依赖阻塞标为 blocked 并给原因/恢复条件；回归或证据失效时带原因重新打开。 |
| durable-checkpoint | HD-STA-001 | 完成有意义的步骤、出现阻塞或产生验证结果时，更新已完成步骤、剩余步骤、最近验证和下一步。检查点粒度应足以接续，又不要求每行代码写日志。 |
| reconcile-before-resume | HD-STA-001 | 新会话先读权威清单与最近检查点，再核对遗留 in_progress 项的实际文件改动和验证证据，之后决定续作、补验证或补状态；正常退出记录缺失不能阻止恢复。 |

文件格式由项目决定：结构化 Markdown、JSON 或已指定的任务系统均可。接受显式映射的等价状态（pending/not_started、in_progress/active、done/passing）；不要强制改名或建立第二份权威清单。单一短任务可在已有规格/任务记录内承载状态，不强制每次新建文件。外部权威系统不可读时保留无法验证，不自动同步或连接外部系统。

## 中断后的处理

1. 确认目标 Worktree、任务和当前差异，读取清单及最近检查点。继续同一未完成任务使用原专用 Worktree；新独立任务才按 Git 工作流规则新建。
2. 优先核对遗留进行中项。状态显示 pending/in_progress，但代码可能已经部分或全部实现；不能据状态标签直接重做。
3. 已实现且验证证据仍适用：补齐缺失的真实状态记录；已实现但尚未验证：先运行已授权的相称检查；部分实现：从剩余步骤继续。无法判断时记录待核验范围。
4. 对部署、发消息、迁移或其他可能有外部副作用的步骤，先核对实际结果与重放条件；未知结果时停止该步骤并说明恢复条件，不盲目重试。
5. 使用当前真实时间记录恢复与补写；不把补测/补状态伪造成中断前已发生。未满足完成条件的项保持进行中或 blocked。

## 判断与证据

先按 [证据分层](evidence-quality.md) 区分规则、执行记录与核验结果。三个控制最低均为 verified，但层级达标不代表所有子检查已满足。

- 只有“先写清单”“做完打勾”的规则：通常部分满足；没有执行记录不能称为流程已执行。
- 有当前状态快照或日志，但不能确认建立、开始、验证、完成的先后：最多说明发现记录，时序无法验证。
- 正常结束时才保存：不满足及时持久化要求；如果已有有效基础，给部分满足并列出缺口。
- 明确发现先标 done 后验证、实现后才标进行中，或状态与实际记录冲突：说明冲突，不能因最后状态为 done 忽略违规顺序。
- 合格恢复记录或经授权的等价中断演练能证明该任务的恢复路径；没有实际异常不代表恢复能力不适用，也不代表验证过。诊断不主动终止进程制造异常。
- 只读扫描未获得关键文件、执行日志或真实状态时，解释限制；不要通过不适用掩盖适用于仓库开发流程的缺口。

## 可选补强内容

用户选择相关控制后，在现有任务规则或清单中加入所缺内容，全部进入最终预览。下面的字段是参考，不是待写入的真实任务记录；占位值不构成执行证据。

| 字段 | 内容 |
| --- | --- |
| id / behavior / acceptance | 稳定任务 ID、目标行为、可验证的完成条件 |
| status / dependencies | 当前状态、依赖与唯一权威位置 |
| checkpoint | 已完成步骤、剩余步骤、下一步、最近更新时间 |
| verification | 实际检查、结果、时间、适用版本/范围、未验证项 |
| blocker | 原因、恢复条件、需要谁处理；无阻塞时明确为空 |
| transitions | 关键状态变化及原因；使用现有记录机制证明先后，不要求引入事件数据库 |

建议补强的规则应明确“实现前规划 → 开始前持久化进行中 → 逐步保存检查点 → 验证 → 及时完成 → 启动时核对恢复”。只添加说明或模板不会自动变成已满足。Doctor 不运行任务调度器，也不在普通开发任务中自动触发；开发 Agent 按仓库中已采用的规则实际维护状态。
