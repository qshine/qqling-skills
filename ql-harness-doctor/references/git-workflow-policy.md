# Git 工作流检查：用户确认规则（2026-09-09）

这两条来自本项目用户的明确要求，不是书籍或厂商适用于所有团队的强制标准。两条最初在目录 0.2.0 引入；当前版本见 [工作流](workflow.md)，沿用 46 个 canonical 控制和 74 个章节别名，不重复计分。旧目录报告须重新判断；因标准加严而下降的分数不代表仓库发生退化。

## 两条独立展示的子检查

| 子检查 | 归属控制与门槛 | 要求 | 典型缺口 |
| --- | --- | --- | --- |
| worktree-per-change | HD-SCP-001，L2 | 每次独立修改任务开始前，新建专用 Git Worktree 和分支；在该目录内完成修改，记录基线、范围和目录 | 只切分支、复用已完成任务的旧 Worktree、直接修改主工作区 |
| commit-after-change | HD-STA-004，L3 | 改动完成并验证后，仅提交本任务改动；交接记录真实提交 SHA、范围和验证结果 | 只有进度文档、留下未提交改动却宣称完成、混入无关改动 |

“每次改动”按独立修改任务计算，不是每改一行就创建工作区或提交。同一未完成任务可以继续使用其专用 Worktree。只读诊断不创建 Worktree；确无文件变化不制造空提交。两个子检查分别列出理由与证据，但只通过各自 canonical 控制参与覆盖率和等级计算，不另加分母。

## 证据与六种状态

- **已满足**：范围内规则完整、一致，且检查到能关联任务、工作区创建先后、基线、改动、验证及提交的记录。仅对实际检查的范围下结论，不从一次成功推断全部历史合规。
- **部分满足**：只有规则而缺少执行记录，或只有分支、进度文件、旧工作区等部分措施。
- **缺失**：在策略允许的完整检查范围内，没有对应规则或任务证据。
- **冲突**：上下级规则矛盾，或任务记录与要求相反，例如允许小修改绕过 Worktree，或宣称已提交但交接显示尚未提交。
- **无法验证**：关键证据在外部、被排除或截断，或无法确认操作顺序、提交对应关系。不能把猜测填为已满足。
- **不适用**：当前检查作用域明确为纯只读或无文件改动任务。对于一般会产生改动的仓库，不能因为本次 Doctor 只读运行就把仓库工作流标成不适用；没有 Git、权限或提交身份是限制/阻塞，不是规避检查的理由。

取证器保持静态只读，不执行 Git log、创建 Worktree 或提交。`.git` 文件只能提示可能处于关联工作区；文档中的 SHA 只是待核实记录，不能单独证明真实提交。若只读取了约定而未获执行证据，就明确报告“规则已声明，执行无法确认”。需要额外操作性核验时，说明精确的只读核验范围，遵守运行环境授权。

默认补强是由用户选择后，预览并确认新增/追加规则和任务交接模板。写出规则不等于实践已经合规，不自动升为已满足。

## Doctor 自己修改仓库时的边界

1. 纯只读诊断不进行任何 Git 写操作。进入补强时，说明专用 Worktree 路径、分支、基线和 Git 元数据影响；没有实际用户授权时先取得准备工作区的授权。用户已明确授权本次创建时，不重复索取同一授权。
2. 在最终文件差异预览前准备本任务的新 Worktree。切换根后，必须重新 scan、assess、select，保留用户已选控制的意图并重新验证依赖；旧根的证据、摘要和确认不能移用。不要自动复制、提交或覆盖原工作区的未提交改动；必需上下文不能安全带入时报告阻塞。
3. 在真实目标工作区展示一次完整文件差异，以及拟提交的精确文件范围、提交说明、验证命令及其副作用。最终确认绑定这份预览；确认后不得换工作区、扩展文件范围或静默刷新摘要。

   Worktree 创建与 Git 提交属于明确展示的 Agent 操作，不属于 PreviewManifest/apply 的机器接口；不得声称文件摘要已经自动验证或授权这些 Git 操作。
4. apply 只写入已确认的新建/追加内容并做静态检查。需要运行的项目检查和本地 Git 提交由 Agent 在授权范围内单独执行。验证通过后仅暂存本任务的明确路径，检查暂存差异，再提交并记录实际 SHA。不全仓库暂存，不推送、合并、改写历史、绕过 hooks 或虚构提交身份。
5. 验证或提交失败时，保留工作并报告未完成/未提交的具体状态；apply 成功不等于提交成功。无文件变化不创建空提交。提交后重新扫描、语义判断与评估，不沿用提交前的证据摘要。
