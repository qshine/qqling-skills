## 忠实摘要

### 核心结论

Harness 不是一个提示词文件，而是模型权重之外支撑执行的完整工程系统。章节用指令、工具、环境、状态、反馈五个子系统建立可操作框架，并强调仓库应成为 Agent 可发现知识的权威入口。

### 关键概念

- **指令**：项目目的、启动路径、硬约束和详细文档路由。
- **工具**：文件、Shell、Git、测试等执行能力及其权限边界。
- **环境**：依赖、运行时版本、服务和可复现配置。
- **状态**：当前进度、阻塞、下一步和跨会话持久化。
- **反馈**：测试、类型检查、Lint、构建和评估结果。
- **地图而非说明书**：入口文件负责导航和不变量，详细知识按需加载。
- **控制变量排除法**：在模型和任务不变时逐个移除组件，观察边际贡献。

### 失败模式

- 把单个长提示词误认为完整 Harness。
- Agent 知道目标却缺少可执行工具，或有工具却无法判断结果是否正确。
- 环境不可复现，导致每次会话重新排错。
- 状态只存在于聊天历史，关闭会话后不可恢复。
- 用组件拆除实验直接宣称找到了瓶颈，忽略真实失败记录。

### 实践建议

- 对五个子系统分别审计，不用单一文件是否存在代替完整性判断。
- 优先建立清晰、可运行的验证反馈。
- 用入口文件路由到项目事实，不在入口重复整本项目手册。
- 把权限设计为最小但足够，既不能无边界开放，也不能让 Agent 无法完成基本工作。
- 定期审计 Harness 腐化，并结合失败记录判断优化优先级。

### 重要限制与反例

- “五个子系统缺一不可”是设计视角；具体控制项仍需按仓库类型判断适用性。
- 反馈通常高回报，不代表所有仓库都应首先补测试；若环境根本无法启动，应先修复环境入口。
- 拆除实验测量的是当前任务下的边际贡献，不足以独立证明因果瓶颈。

### 可能状态判断

- **已满足**：五个子系统有相互一致且可操作的证据。
- **部分满足**：有工件但缺路由、命令、状态更新约定或权限边界。
- **缺失**：一个适用子系统没有任何证据。
- **冲突**：入口与实际脚本、版本或权限配置不一致。
- **无法验证**：只能看到描述，不能确认命令或环境有效。
- **不适用**：例如短期一次性仓库可以不要求持久进度状态。
