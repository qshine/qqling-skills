## 忠实摘要

### 核心结论

Loop Engineering 建立在可靠的单次 Harness 之上，把人从逐轮触发者变成目标、验证、停止条件和异常边界的设计者。最小循环由可验证目标、执行/反馈循环和有界停止规则组成；随着自主时间和并行度增加，还必须加入独立检查、外部状态、隔离、预算及人工升级机制。

### 关键概念

- **目标驱动循环**：给出最终状态而非下一步动作，持续迭代直至达标或触发停止条件。
- **时间/事件驱动循环**：按时间或外部事件重复执行相对独立的动作，与累积进度的目标循环不同。
- **Generator/Evaluator 分离**：实现者和停止判断者使用不同角色及上下文。
- **外部状态**：将轮次、结果、阻塞和下一步保存在单次对话之外。
- **工作区隔离**：并行执行时用独立分支或 worktree 防止机械冲突。
- **六类原语**：自动触发、工作区、技能、连接器、子 Agent 和外部状态共同支撑循环。
- **沉默成本**：验证负债、理解腐烂、认知投降和上下文/令牌膨胀会随循环持续累积。

### 失败模式

- 目标不可测量，循环由执行者凭感觉决定何时完成。
- 把需要累积进度的目标错误放入无记忆的周期轮询，每次从头开始。
- 没有最大轮次、预算、无进展检测或人工升级，导致无限消耗。
- Maker 与 Checker 共享同一推理上下文，独立复核名存实亡。
- 多个 Agent 共用工作区或含糊所有权，产生冲突和覆盖。
- 自动执行拥有超出目标需要的写入、合并或外部消息权限。
- 产出速度超过人类理解和审阅能力，验证债务持续增长。

### 实践建议

- 从重复、范围窄、结果可验证的任务开始，不直接建设自主任务工厂。
- 每个目标同时声明验收、可改/不可改范围、验证顺序和停止条件。
- 设置最大轮次、时间/费用预算、连续无进展阈值和人工介入条件。
- 每轮读取并更新持久状态，保留失败实验和下一步，而不只保留成功结果。
- 为并发工作分配隔离工作区和明确文件/模块所有权。
- 独立 Checker 只读取必要交付物和证据，逐项给出可追溯结论。
- 监控循环的验证债务、上下文增长和人工审阅积压。

### 重要限制与反例

- 章节用具体产品命令解释概念，但控制项不应绑定 `/goal`、`/loop` 或某个平台的当前实现。
- “Maker 与 Checker 必须永远分离”对低风险小任务可能成本过高，应由风险和自主程度触发。
- 自动合并或“永不停止”只适合极窄、可回滚、强验证的实验环境，不应成为通用开发默认值。
- worktree 解决文件碰撞，不解决语义冲突、集成风险和审阅瓶颈。
- 外部连接器扩大行动范围，也同步扩大权限、隐私和误操作风险。

### 可能状态判断

- **已满足**：循环有界、可验证、可恢复，权限与复核机制匹配风险。
- **部分满足**：存在自动化，但缺状态、预算、独立检查或升级路径。
- **缺失**：无人值守循环依赖执行者自报完成或无限重试。
- **冲突**：自动化目标、权限、停止规则或多个状态源互相矛盾。
- **无法验证**：循环由外部平台托管，仓库内没有配置、链接或运行契约。
- **不适用**：仓库尚无无人值守或多轮自动开发需求；这是多数 MVP 仓库的正常状态。
