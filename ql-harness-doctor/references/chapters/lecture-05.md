## 忠实摘要

### 核心结论

上下文窗口无论多大都不是可靠的长期状态存储。跨会话任务必须把进度、关键决策及其原因、验证结果和下一步持久化到仓库，否则新会话会重复探索、改变既有决策并累积漂移。好的连续性设计追求低重建成本和随时可接手。

### 关键概念

- **状态持久化**：把跨会话必须保留的信息写入稳定工件。
- **重建成本**：新会话恢复到可以继续执行所需的时间和上下文。
- **漂移**：Agent 对目标、决策和代码现状的理解逐次偏离。
- **上下文焦虑**：上下文接近上限时出现赶工、跳过验证或提前收尾。
- **压缩与重置**：压缩保留部分连续性但可能丢失原因；重置依赖完备交接重建干净上下文。
- **检查点**：用原子 Git 提交保留可恢复的已验证状态。

### 失败模式

- 进度只记录“做了什么”，没有“为什么这样做”。
- 测试失败、未验证路径和阻塞没有进入交接。
- 新会话重新实现已完成工作，或推翻有意的设计选择。
- 长任务仍完全依赖聊天历史或自动摘要。
- 状态文件长期不更新，形成比缺失更危险的错误事实。

### 实践建议

- 维护当前状态、已完成、进行中、阻塞和下一步明确的进度工件。
- 对重要决策记录选择、原因、否决方案和仍然有效的约束。
- 会话结束前保存验证结果和干净检查点，会话开始时先读取并核实。
- 短任务允许会话内完成；长任务在上下文耗尽前主动准备交接。
- 用全新会话恢复实验衡量重建成本和歧义点。

### 重要限制与反例

- 固定的时间或上下文比例只能作为信号，不能跨模型、任务和工具机械套用。
- 状态文件不是越多越好；进度、决策和验证可以按仓库规模合并，只要语义清晰。
- Git 历史能说明发生了什么，但通常不能替代当前阻塞和下一步说明。

### 可能状态判断

- **已满足**：新会话可从仓库确定状态、原因、验证和下一步。
- **部分满足**：有进度记录，但缺决策原因、验证结果或更新约定。
- **缺失**：连续性只依赖聊天历史。
- **冲突**：状态工件、Git 状态和功能清单对进度描述不同。
- **无法验证**：模板存在但没有近期更新或恢复实验。
- **不适用**：短期一次性任务可不要求完整跨会话体系。
