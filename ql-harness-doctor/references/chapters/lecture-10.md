## 忠实摘要

### 核心结论

局部组件分别通过测试，不能证明它们组合后的用户流程正确。Harness 应根据变更表面选择覆盖真实边界的集成或端到端验证，并把关键架构不变量与重复审查意见提升为可执行规则，从而同时改变结果质量和 Agent 的实现行为。

### 关键概念

- **组件边界缺陷**：单个模块正确，但接口、状态、资源或错误在跨层传播时失效。
- **测试充分性梯度**：单元、集成、端到端验证覆盖不同缺陷面，不可互相简单替代。
- **架构边界执行规则**：把依赖方向、安全边界等文档约束编码为自动检查。
- **审查反馈提升**：把重复出现的人工意见转化为永久测试或 lint 规则。
- **面向 Agent 的错误消息**：同时表达问题、原因和可行修复路径。
- **执行不变量而非微管实现**：约束必须守住的边界，给具体实现保留空间。

### 失败模式

- 单元测试大量使用 mock，掩盖真实接口和环境不匹配。
- 没有覆盖跨组件状态传播、资源生命周期、权限及错误路径。
- 架构原则只写在文档中，Agent 继续复制仓库里的坏模式。
- 所有任务都机械要求同一种端到端测试，造成昂贵且低价值的验证。
- 审查中不断出现同类意见，却没有沉淀为 Harness 能执行的防线。

### 实践建议

- 先声明架构边界，再为高价值用户路径建立跨层验证。
- 根据变更涉及的组件和副作用决定单元、集成、端到端层级。
- 将边界规则实现为确定性检查，并给失败消息附修复指引。
- 记录重复审查意见，达到阈值后提升为规则或回归测试。
- 端到端测试应验证真实结果和副作用，不只验证 UI 元素存在。

### 重要限制与反例

- “只有端到端测试能证明系统级缺陷不存在”是强表述；有限测试无法证明缺陷不存在，只能提高对特定流程的信心。
- 端到端测试通常较慢且可能不稳定，不应取代单元和集成测试。
- 小型库、纯算法包或无用户流程的仓库可能不适用 UI 型 E2E，但仍可能需要跨模块契约测试。
- 架构规则的机械检查只覆盖可表达的不变量，不能取代设计审查。

### 可能状态判断

- **已满足**：验证矩阵覆盖适用边界，关键架构规则可执行。
- **部分满足**：存在 E2E 或架构文档，但覆盖、适用规则或自动执行不完整。
- **缺失**：仅有孤立单元测试，跨层改动没有对应验证。
- **冲突**：文档允许的依赖或流程被自动规则禁止，或反之。
- **无法验证**：存在测试名称或脚本声明，但无法从仓库判断其真实覆盖路径。
- **不适用**：仓库没有可识别的跨组件用户流程；应记录理由而非强造 E2E。

### 仍需讨论

- 第一版如何仅凭静态仓库证据判断 E2E 是否真的穿过真实边界？
- 审查意见出现几次后应建议机械化，是否需要由团队自行设阈值？
