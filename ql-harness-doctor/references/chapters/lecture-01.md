## 忠实摘要

### 核心结论

模型在基准任务上的能力不等于在真实仓库中的执行可靠性。需求含糊、隐性约定、环境缺口、验证缺失和跨会话失忆，都可能让能力足够的模型失败。遇到失败时，应先把问题归因到 Harness 的具体层，而不是立即换模型。

### 关键概念

- **能力鸿沟**：模型理论能力与真实任务表现之间的差距。
- **Harness 诱导失败**：模型有能力完成任务，却被外部工作系统的结构缺陷拖垮。
- **验证缺口**：Agent 的完成声明与可验证结果不一致。
- **诊断循环**：执行、观察、归因、修补 Harness、重新执行。
- **完成定义**：能够由测试、静态检查、构建或业务验收证明的完成条件。
- **五层失败来源**：任务规范、上下文供给、执行环境、验证反馈、状态管理。

### 失败模式

- Agent 必须猜测需求、架构或运行方式。
- 团队约定只存在于人脑或外部聊天记录中。
- 大量上下文被依赖和环境排错消耗。
- 只完成可见外壳，未跑通完整工作流便宣布完成。
- 新会话无法迅速理解前一会话的工作和剩余事项。

### 实践建议

- 把任务写成带有明确输入、输出、边界和可执行验收条件的规格。
- 在仓库入口记录技术栈、架构约束与验证命令。
- 记录 Agent 任务是否成功、失败属于哪一层，并持续修补重复失败点。
- 用同一模型和同一任务做前后对照，验证 Harness 改进是否真的有效。

### 重要限制与反例

- 失败优先检查 Harness，不等于模型永远不是瓶颈；应基于同类任务和失败证据归因。
- 存在 `AGENTS.md` 只证明有入口文件，不证明规则完整、正确或被遵循。
- 章节中的成功率和效率案例用于说明机制，不能直接成为所有仓库的预期收益。

### 可能状态判断

- **已满足**：规则存在，并能找到近期任务中的执行证据。
- **部分满足**：只有口头式要求或只有命令，没有完成门槛。
- **缺失**：没有规格、验证或连续性信息。
- **冲突**：不同文件给出不同完成条件或运行方式。
- **无法验证**：规则存在，但找不到可运行命令或结果。
- **不适用**：仅对跨会话控制项适用；一次性实验仓库可排除连续性要求。
