## 忠实摘要

### 核心结论

功能清单不只是备忘录，而是调度、验证、进度和交接共同依赖的外部化状态原语。每个工作项必须把目标行为、验证方式和当前状态绑定起来，并以验证证据控制进入通过状态，避免 Agent 使用自己的隐式标准宣布完成。

### 关键概念

- **功能清单原语**：供调度器、验证器、交接器和进度追踪共同读取的结构化事实。
- **行为—验证—状态三元组**：说明做什么、怎样证明、目前在哪里。
- **状态机**：`not_started`、`active`、`blocked`、`passing` 等显式状态与受控转换。
- **通过门控**：只有预期工作流被执行并记录成功证据后才允许通过。
- **单一权威来源**：范围和进度不应在多个互相矛盾的位置独立维护。
- **粒度校准**：工作项应能在可控会话内形成行为闭环。

### 失败模式

- 使用“基本完成”等无法恢复和验证的模糊状态。
- 工作项只有标题，没有行为、验证或证据。
- Agent 可以直接把状态改成通过而不运行验证。
- 功能清单、聊天、TODO 和计划文件对范围给出不同答案。
- 清单粒度过粗导致长期 active，或过细导致管理噪声。

### 实践建议

- 使用机器可读或严格结构化的清单，并为条目分配稳定 ID。
- 把行为、验证、状态、证据及必要依赖放在同一工作项中。
- 限制 active 数量，并让验证结果驱动状态转换。
- 从清单生成进度和交接摘要，避免重复维护状态。
- 用实际工作流验证功能，不以语法通过或文件存在代替行为正确。

### 重要限制与反例

- 章节把 `passing` 描述为不可逆，但真实仓库可能因回归、依赖变化或证据失效需要重新打开；最终设计必须保留失效机制。
- 并非所有仓库都需要 JSON；小型项目可以使用结构可靠的 Markdown 或现有 issue 系统镜像。
- “所有该做什么的信息都来自一个文件”不应抹去产品规格和 issue；应指定状态权威并建立链接关系。

### 可能状态判断

- **已满足**：清单结构完整，状态由证据驱动且权威明确。
- **部分满足**：有清单，但条目缺验证、证据、依赖或状态规则。
- **缺失**：范围和进度仅存在于对话或自由文本中。
- **冲突**：多个状态源对同一工作项结论不同。
- **无法验证**：声明门控但找不到执行器或验证记录。
- **不适用**：单一、短期、一次性任务可不建立完整功能状态机。

### 仍需讨论

- 第一版支持哪些已有清单格式，哪些只报告为“外部权威、无法验证”？
- 状态回退是对书中规则的有意修正，需在最终计划中明确依据和兼容策略。
