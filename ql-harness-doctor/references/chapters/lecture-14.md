## 忠实摘要

### 核心结论

当多个 Agent、循环、确定性工具和人工决策之间出现专业分工、并行、回退与共享状态时，隐含在单循环中的控制流应被显式建模为图。图的价值不在视觉形状，而在责任、路由、状态合并、锚点、检查点、恢复和否决权变得可读、可审计和可局部修复；协调收益不足时不应图化。

### 关键概念

- **节点、边、共享状态、路由**：图的四个基本构件，分别表示职责、交接、公共事实和下一步选择。
- **私有上下文与共享状态分离**：节点不共享完整对话，只通过定义过的状态字段协作。
- **Graph 与 Workflow**：确定性代码控制全部流程时是 workflow；含自主 Agent 和动态路由时，图泛化了传统工作流。
- **回退与否决边**：明确验证失败、信息不足和人工拒绝后返回哪个节点。
- **检查点与恢复**：每步持久化状态，使执行可中断、重放和继续。
- **锚点**：用真实业务结果、ground truth 或人工抽查约束局部指标，抵抗 Goodhart 效应。
- **编排税**：Agent 并行容易，人类理解、整合和审阅仍是串行瓶颈。

### 失败模式

- 单循环同时设定目标、执行和评价，无法质疑自身指标或方向。
- 多个局部优化循环目标冲突，各自健康却损害整体结果。
- 并行节点写同一状态字段，但未定义覆盖、追加或归并语义。
- 验证节点继承实现者完整上下文，独立审查失效。
- 图有精美拓扑，却缺少重放、观察、恢复、预算和失败出口。
- 只优化易测代理指标，没有连接真实用户或业务结果的锚点。
- 节点数量超过审阅和集成能力，编排成本高于并行收益。

### 实践建议

- 先用适用性判据证明需要图，再选择框架或画拓扑。
- 为每个节点声明职责、输入、输出、私有上下文、工具、预算和完成标准。
- 为每条边声明触发条件、失败/回退路径、重试上限和责任人。
- 为共享状态定义 schema、字段所有者、并发合并语义与版本。
- 验证节点使用新鲜上下文，只接收必要状态和可追溯证据。
- 在关键副作用前保存检查点，并为合并、发布等动作设置人工门槛。
- 用真实结果或人工抽样校准指标，持续核算审阅积压和协调成本。

### 重要限制与反例

- 图工程是对已有 workflow、状态机和多 Agent 模式的重新组织，不应因新术语而默认引入框架。
- 步骤很多但完全线性的任务通常只需要脚本或普通 workflow。
- 章节建议“五项至少满足三项”是实用启发式，不是经验证的普适阈值；Doctor 应把它作为建议适用门槛。
- 图引擎提供节点、边和 checkpoint，不会替团队决定目标、权力、证据和责任。
- 单个可靠循环可以视为一节点图，但这种表述不能成为增加编排层的理由。

### 可能状态判断

- **已满足**：图有明确适用依据，控制流、状态、恢复、锚点与审阅容量均可追溯。
- **部分满足**：有编排代码或图示，但缺失败边、状态语义、恢复或现实锚点。
- **缺失**：复杂多 Agent 系统依赖隐式聊天交接和共享工作区。
- **冲突**：图示、编排实现与节点责任或状态 schema 不一致。
- **无法验证**：图运行在外部平台，仓库只留下名称而无版本化规范。
- **不适用**：未达到图化门槛，使用单 Agent、脚本或线性 workflow 更合适。
