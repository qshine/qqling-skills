Harness Doctor 的目标是：在用户当前打开的**一个仓库**中，识别 Agent 开发 Harness 的规范缺口，以可追溯证据给出分组建议；用户选择需要补强的控制项后，统一预览全部文件差异，再确认一次执行修改与验证。

主要用户包括独立开发者、Tech Leader 和平台工程师。三类用户共享同一控制目录，报告的解释重点不同：独立开发者偏重低成本最小闭环，Tech Leader 偏重一致性和质量门槛，平台工程师偏重可复用治理与高级编排。不得为不同角色复制三套互相漂移的规则。

核心成功指标是**适用规范覆盖率提升**，而不是生成文件数量、指令长度或工具数量。

## 2. 产品边界

### 2.1 单仓库边界

- 一次调用只诊断当前仓库根目录，不扫描兄弟目录、其他 worktree 或用户的多个仓库。
- 可以识别 monorepo 内的多个模块，但它们仍属于同一个仓库；作用域文档应靠近对应模块。
- 仓库外事实只能通过仓库中的权威链接或用户明确提供的信息表达。MVP 不主动读取 GitHub、工单系统、CI 服务、日志平台或云配置。

### 2.2 可修改边界

以下列表保留原研究愿景；本版自动应用的精确白名单以 [Skill 入口](SKILL.md) 和 change-preview Spec 为准。CI、依赖和业务逻辑均不自动修改，需要单独明确授权的任务。用户已有未提交内容按字节保留，可预览追加，不覆盖既有内容。

用户确认后，Skill 只可补强 Harness 和工程脚手架，例如：

- Agent 入口与路由文档；
- 架构、约束、决策、进度、交接和任务模板；
- 已有安装、启动、测试、Lint、类型检查的统一入口或薄封装；
- 安全且确定性的仓库检查器；
- 用户明确选择时的 CI 质量门配置。

默认不可修改：

- 业务功能、产品行为、数据库 schema 和生产配置；
- 依赖版本、部署流程、权限边界及外部系统状态；
- 用户已有未提交变更；
- 任何未在统一预览中展示的文件或命令。

如果某个补强动作必须越过上述边界，报告应标记为“需要单独项目”，不能借一次最终确认隐式扩大权限。

### 3.3 章节冲突与裁决

以下不是简单取一章覆盖另一章，而是明确产品规则：

1. **“通过不可逆”与证据失效**：L08 强调通过状态的门控，但长期仓库会发生回归。产品允许 `passing` 在依赖变化、回归失败、证据过期或规范改变时重新打开，并记录失效原因。
2. **“所有测试必须通过”与既有红灯**：L12 的清洁目标保留，但不得迫使用户顺手修复无关历史失败。判断采用“目标基线全绿；若已有正式失败基线，则不得新增失败并必须显式交接”。
3. **WIP=1 与并行 Agent**：L07 的 WIP=1 是默认安全门槛。只有具备工作区隔离、明确所有权、状态隔离和集成门后，L03/L13 的并行模式才可替代它。
4. **仓库唯一事实来源与外部系统**：L03 不要求复制所有外部内容。仓库保存会改变 Agent 决策的结论、责任和权威链接；若外部内容无法读取，状态为“无法验证”，而不是“缺失”。
5. **E2E 必需与验证适用性**：L09/L10 的系统级验证按变更表面触发。无跨组件流程的库可以使用契约或集成测试，不机械要求 UI E2E。
6. **独立 Checker 必需与成本**：L09/L13 的独立复核在高风险、长时自主、跨组件或主观验收任务中成为门槛；低风险局部任务可使用同一 Agent 的显式自检，不因此扣到 L0–L3。
7. **指令文件长度**：L04 的行数经验不转化为硬阈值。Doctor 判断主题混合度、重复、冲突、路由和任务相关性，长度只作提示证据。
8. **图化“三选五”**：L14 的五项至少满足三项作为建议性适用门槛，不作为普适数学定律。若协调收益无法证明，优先脚本、workflow 或单循环。

## 4. L0–L4 成熟度模型

成熟度按门槛而非平均分判定。仓库达到某一级，必须满足该级全部**适用的门槛控制**以及所有更低等级门槛；可选控制不阻断等级。

| 等级 | 名称 | 等级门槛 |
| --- | --- | --- |
| L0 | 未准备 | 无法可靠发现仓库目的、启动或基本验证；或关键证据互相冲突，以致 Agent 只能猜测 |
| L1 | 可发现、可启动 | 有短入口/地图；仓库目的和权威事实可发现；适用的安装、启动、基本验证命令明确；现有检查与文档不互相矛盾 |
| L2 | 有边界、可接续 | 任务有范围、非目标和完成定义；进度、关键决策、阻塞、验证和下一步可持久恢复；工作清单权威明确；单 Agent 默认限制 WIP |
| L3 | 可验证、可维护 | 完成由适用的分层检查和证据门控；跨组件路径与架构不变量有相称验证；错误可操作；运行/过程可诊断；退出清洁且不新增基线失败；清理安全 |
| L4 | 可自治、可协调 | 仅在明确采用自动循环或图时评定：运行有目标、预算、停止与人工升级；状态可恢复；实现与验证适当隔离；权限最小化；并行有所有权；图有路由、检查点、锚点和审阅容量 |

判定补充规则：

- 没有自动循环或图需求的仓库，正常上限是 `L3（L4 未启用）`，不能因为所有 L4 项都“不适用”而自动获得 L4。
- L4 的某些控制不适用时可从覆盖率分母移除，但至少要有一个已采用的自治场景，并满足该场景全部核心门槛，才可声明 L4。
- 一个高级能力存在但安全门槛缺失时，等级可能仍是 L3，但报告必须把该 L4 风险放在最高优先级，而不是用平均覆盖率淡化。
- 成熟度表达“可依赖程度”，不表达团队或模型能力高低。

## 5. 六种诊断状态

每个适用控制项只产生一个主状态，并附来源、仓库证据、判断理由和补强建议。

| 中文状态 | 机器值 | 定义 |
| --- | --- | --- |
| 已满足 | `satisfied` | 证据完整、一致，满足控制要求 |
| 部分满足 | `partial` | 有有效基础，但缺少必需字段、范围、执行链或维护机制 |
| 缺失 | `missing` | 适用且在允许读取范围内找不到相关证据 |
| 冲突 | `conflict` | 两个或以上权威候选对同一事实给出不兼容结论 |
| 无法验证 | `unverifiable` | 有声明或外部引用，但当前只读仓库证据不足以确认真实性或新鲜度 |
| 不适用 | `not_applicable` | 根据仓库类型和使用场景明确排除，并记录理由 |

判断顺序是：先确定适用性；再检测冲突；然后判断证据是否可验证；最后区分满足、部分和缺失。`无法验证` 不能被用来掩盖实际不存在的证据，`不适用` 也必须有具体理由。

## 6. 规范覆盖率

总体覆盖率定义为：

```text
规范覆盖率 = 已满足控制项数量 /（全部控制项数量 - 不适用控制项数量）× 100%
```

规则：

- 只有“已满足”进入分子。
- “部分满足”“缺失”“冲突”“无法验证”都保留在分母。
- “不适用”不进入分母。
- 分母为零时显示 `N/A`，不显示 100%。
- MVP 不做风险权重平均；同时报告各状态数量、各控制域覆盖率和成熟度门槛，避免一个总分掩盖关键缺口。
- 补强完成后使用同一目录版本重新诊断，给出前后覆盖率和状态变化；来源版本不同的结果不得直接比较。

覆盖率是改进指标，不是自动放行门。存在高风险冲突或已启用自治能力的关键门槛缺失时，即使覆盖率较高也必须醒目标记。

## 7. 混合诊断架构

### 7.1 Python 只读取证

确定性脚本负责收集事实，不作语义裁决。计划中的主要输出是结构化 JSON，包含：

- 仓库根、Git 状态和可读取作用域；
- Agent 指令、README、架构/决策/进度/交接文件候选；
- 语言与包管理清单、版本文件、任务运行器和脚本名称；
- 测试、Lint、类型检查、构建、E2E、CI 及架构检查候选；
- 自动化、工作区、状态、可观测配置和维护任务候选；
- 文件路径、行号、摘要、mtime/内容哈希等可追溯信息。

取证器的安全约束：

- 诊断阶段不执行仓库脚本、安装依赖、启动服务、访问网络或写入目标仓库。
- 默认跳过 `.git` 对象、依赖目录、构建产物、二进制、大文件、密钥和 `.env*` 内容。
- 不跟随逃出仓库根的符号链接；读取失败时记录原因，不扩大权限。
- 只识别命令声明，不能把“命令存在”写成“命令已通过”。
- 使用 Python 标准库优先，保证在 Python 3.9+ 下可运行并降低安装成本。

### 7.2 Agent 语义判断

Agent 读取控制目录与取证 JSON，负责：

1. 推断仓库类型、风险和适用控制项；
2. 识别同义文件、语义冲突和文档是否回答了控制要求；
3. 为每个状态引用具体仓库证据，区分事实与推论；
4. 合并重复建议，标注依赖关系和预期收益；
5. 生成用户可理解的分组报告和候选补强方案。

Agent 不得仅凭文件名判定“已满足”，也不得在证据不足时猜测外部系统状态。

## 8. 交互与变更事务

固定流程如下：

```text
只读诊断
  → 分组建议
  → 用户选择控制项
  → 统一差异预览
  → 最终确认一次
  → 修改与验证
```

### 8.1 只读诊断

- 先说明扫描范围、来源目录版本和不会执行的动作。
- 输出成熟度、总体/分域覆盖率、六种状态和证据引用。
- 不在目标仓库创建报告、缓存或临时文件。

### 8.2 分组建议与选择

建议按基础入口、知识与指令、任务与状态、验证与架构、可观测与清洁、高级自治分组。每项展示：稳定控制 ID、当前状态、证据、预期改动文件、依赖项、风险和收益。

用户勾选控制项，而不是直接勾选文件。若所选项依赖另一个缺失控制，预览前明确列出依赖；未经用户选择不得自动扩大范围。

### 8.3 统一差异预览

- 在系统临时目录生成候选文件，不修改目标仓库。
- 记录所有目标文件的原始内容哈希和存在状态。
- 一次展示完整 unified diff、将执行的安全验证命令、不会执行的动作及可能副作用。
- 新文件显示完整内容；修改文件显示上下文差异；删除或覆盖默认不进入 MVP。

### 8.4 最终确认一次

最终确认覆盖预览中的全部文件与验证命令。确认后如果原始文件哈希、分支或工作树状态发生漂移，必须停止并重新预览，不能套用旧确认。

### 8.5 修改与验证

- 只应用用户选择且已预览的差异。
- 不覆盖诊断开始前已存在的用户改动；发生重叠时停止并报告。
- 仅运行预览中列出的安全验证。安装依赖、访问网络、启动持久服务、部署或写外部系统仍需独立授权，不能被一次确认隐含包含。
- 验证失败时保留清晰状态和修复建议，不静默回滚，也不擅自继续改业务代码。
- 结束报告列出实际修改、验证结果、未解决项、覆盖率变化和恢复方式。

## 9. 控制目录与来源扩展机制

下一阶段建议使用机器可读文件作为运行时目录：

```text
ql-harness-doctor/
├── SKILL.md
├── agents/openai.yaml
├── references/
│   ├── catalog/
│   │   ├── controls.json
│   │   ├── controls.schema.json
│   │   └── sources.json
│   └── chapters/...
├── scripts/
│   ├── collect_evidence.py
│   ├── validate_catalog.py
│   └── render_preview.py
└── tests/
```

每个控制项至少包含：

- `id`、标题、控制域、成熟度、是否为等级门槛；
- 规范陈述、适用条件、不适用条件；
- 证据提示、反证/冲突提示、补强动作；
- 依赖、冲突、替代和废弃关系；
- `source_refs`：来源 ID、文档标题、URL、固定版本、章节/段落、读取日期；
- `source_aliases`：本轮的 `Lxx-Cyy` 等研究 ID；
- 目录 schema 版本和控制项首次/最后变更版本。

来源扩展规则：

1. 本书固定提交作为 `walkinglabs-he@77e7a3e` 的首个来源快照。
2. 后续 OpenAI、Anthropic、论文和项目实践各自拥有独立来源记录与固定版本；网页若无提交 SHA，记录发布日期、读取日期和归档标识。
3. 新来源先与现有控制做语义比对：支持同一要求时追加来源，不复制计分项；提出新要求时创建新稳定 ID。
4. 来源冲突必须并存记录，增加明确的产品裁决及理由，不能按导入顺序静默覆盖。
5. 稳定 ID 不重用；废弃项保留 `superseded_by`，历史诊断仍能解释。
6. 每次诊断记录 `catalog_version` 和来源快照，保证结果可重现。
7. 章节长笔记是研究依据，不应每次完整加载进 Agent 上下文；运行时只加载适用控制及其短来源摘要。

### 阶段 A：规格与目录

## 11. MVP

MVP 包含：

- 对当前单一仓库进行不执行项目命令的静态只读诊断；
- 支持 L0–L3 的核心门槛和覆盖率，识别 L4 是否存在及其高风险缺口；
- 六状态、文件/行号证据、冲突与无法验证说明；
- 按控制域分组建议，允许用户选择部分控制项；
- 在目标仓库外生成完整差异预览；
- 一次最终确认后补充文档、模板和已有工具的安全薄封装；
- 修改后执行预览过的安全验证并重新计算覆盖率；
- L13/L14 只做高级能力诊断和设计建议，不在 MVP 自动创建循环、自动化、子 Agent 图、外部连接器或自动合并流程。

建议默认目标是先帮助仓库达到 L2，再根据真实运行证据补 L3。L4 必须由用户主动表达自治需求。

## 12. 明确不做

- 不做跨仓库批量扫描、组织排行榜或平台级策略下发。
- 不把本书示例原样复制为统一模板，也不承诺书中案例收益。
- 不根据文件名存在直接判定满足，不运行未经确认的项目命令。
- 不读取 `.env`、凭据、用户目录、外部聊天或私有平台数据。
- 不自动安装测试框架、修改业务代码、升级依赖、部署或写外部系统。
- 不自动删除临时文件、TODO、日志、未提交改动或“不整洁”代码。
- 不使用加权总分掩盖门槛缺口，不把行数、文件数量或 E2E 数量作为机械质量指标。
- 不在 MVP 生成或启动 L13/L14 的自主循环和图编排。
- 不在本研究阶段创建可安装 Skill。

## 13. 主要风险与缓解

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| 清单投机 | 为拿分创建空文件，实际能力未提升 | 要求内容证据、执行链和一致性；文件存在最多算候选 |
| 适用性误判 | 小仓库被强推企业级流程 | 先推断仓库类型；不适用必须有理由；L4 默认不启用 |
| 文档陈旧 | 错误规则比缺失更危险 | 冲突/无法验证状态、来源与更新时间、文档—代码联动建议 |
| 规则来源冲突 | 用户不知道该信哪一条 | 并存来源、显式产品裁决、版本化变更记录 |
| 预览后漂移 | 确认的 diff 与实际应用不同 | 原文件哈希、分支和 Git 状态复核；漂移即重新预览 |
| 覆盖用户工作 | 丢失未提交内容 | 诊断前记录状态、目标级重叠检查、禁止自动覆盖和删除 |
| 误执行不可信命令 | 安装、网络或生产副作用 | 诊断零执行；验证命令完整预览；副作用命令另行授权 |
| 控制项过多 | 报告噪声、用户无从选择 | 语义去重、按成熟度和控制域分组、优先显示阻塞下一等级的项 |
| L4 过度工程 | 编排税超过收益 | 高级适用门槛、诊断优先、用户主动启用、审阅容量约束 |
| 来源持续变化 | 相同仓库结果不可复现 | 固定版本、目录版本、结果记录来源快照 |

## 14. 验证方法

### 14.1 目录与来源

- 目录 schema 校验通过，稳定控制 ID、章节 alias 和来源 ID 全局唯一。
- 每个控制项至少有一个固定来源；所有 L01–L14 候选项均被映射或显式标记为不采纳并说明理由。
- 来源冲突测试确认不会静默覆盖，废弃控制仍可解析历史报告。

### 14.2 取证安全

- 运行取证前后目标仓库内容哈希和 Git 状态不变。
- symlink 逃逸、大文件、二进制、依赖目录、构建目录、`.env*` 和凭据 fixture 均不会被读取或泄露。
- 命令声明只被记录，不在诊断中执行。

### 14.3 判定正确性

- 每种状态至少有正反 fixture：完整、部分、缺失、冲突、外部不可验证、不适用。
- 覆盖率测试确认只有 `satisfied` 进入分子，`not_applicable` 排除，零分母为 `N/A`。
- 成熟度测试确认等级逐级门控，L4 不会因全部不适用而自动获得。
- 冲突案例覆盖本计划 3.3 节的八项裁决。

### 14.4 交互与修改安全

- 只读诊断、未选择、取消确认三种路径都不修改目标仓库。
- 选择部分控制时，预览和实际修改都只包含所选 ID。
- 预览后目标变化会强制停止并重新生成 diff。
- 所有实际文件都曾出现在统一预览；验证命令与预览完全一致。
- 脏工作树与修改重叠时停止，不覆盖用户内容。

### 14.5 行为评估

- 用全新 Agent 会话在独立开发者、Tech Leader、平台工程师三个视角运行同一批 fixture。
- 检查报告是否能说明“缺什么、证据是什么、为什么重要、补什么会改哪些文件”。
- 对同一仓库重复运行应得到稳定结论；补强后覆盖率只因对应证据变化而改变。
- 对 L13/L14 普通仓库应返回“不适用”或“未启用”，不能制造伪缺口；已启用自治仓库则必须暴露停止、权限、恢复和审阅风险。

## 15. 待确认问题与建议默认值

1. **MVP 的 L4 策略**：建议只诊断和提出设计建议，不自动生成循环或图。
2. **历史运行证据**：建议 MVP 只认仓库内可追溯证据；外部 CI/任务系统标记“无法验证”，未来通过可选连接器扩展。
3. **输出持久化**：建议只读诊断默认在对话中展示，不写报告文件；用户选择补强后，是否落盘报告也纳入统一预览。
4. **现有任务格式**：建议先支持 Markdown、JSON 和仓库内明确链接的外部权威，不强制迁移到 `feature_list.json`。
5. **CI 修改**：建议作为独立可选分组，默认不选择，避免一次 Harness 初始化改变合并门槛。
6. **新测试框架**：建议 MVP 不安装；只整合已有检查。没有测试框架时给出下一阶段项目建议。
7. **控制目录版本策略**：建议从 `0.1.0` 开始，目录规则变化使用语义化版本并记录迁移说明。
8. **覆盖率目标**：建议不设跨仓库统一及格线；用“达到下一成熟度还缺哪些门槛”驱动行动。

上述问题是研究时的建议默认值；已批准能力地图与控制目录 Spec 已固定 L4 只诊断、静态仓库内取证、只读默认不落盘、单目录版本和不设统一覆盖率及格线。其余交互细节须在各自模块 Spec 中落实；不能把本节的建议当作已经实现或已批准的具体执行接口。
